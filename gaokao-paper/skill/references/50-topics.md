# 题型标签与知识点归属

## 三层职责（重要）

```
大知识点（一级）  ── 纯目录，无 ID，不参与索引
小知识点（二级）  ── 纯目录，无 ID，不参与索引
题型（三级）      ── 实体节点，有 ID，与题目双向多对多
```

**索引只发生在题型和题目之间**，大/小知识点只负责组织和筛选。

所以录入时：

| 字段 | 填什么 |
|---|---|
| `kp` | 一级知识点名 |
| `kp2` | 二级知识点名 |
| `topics` | 题型节点 **ID** 列表（不是名字） |

## 查目录

```bash
python3 py/main.py kp-catalog                    # 六科全部
python3 py/main.py topic-list --subject 数学      # 数学题型节点
```

import sys; sys.path.insert(0, 'py')
import kp_catalog as K

K.topic_label('M-T-050')      # 题型名
K.normalize('数学', '圆锥曲线') # → '解析几何'（别名归一）

## 别名归一

同一考点写法不统一会被拆成两个考点，统计分散、筛选漏题。
已内置 213 条别名（数学 30 / 物理 52 / 化学 41 / 生物 54 / 语文 22 / 英语 14）：

```python
K.normalize('数学', '圆锥曲线')                 # → '解析几何'

```

**填 `kp` / `kp2` 时用标准词。** 不确定就先跑 `normalize` 确认。

## 复合题型（多父）

35 个题型同时属于多个一级知识点：

```
数列与导数        主：函数与导数/导数压轴小题    交叉：数列
立体几何中的轨迹   主：解析几何/轨迹方程          交叉：立体几何
集合与排列组合概率  主：集合与逻辑/集合运算         交叉：概率统计、计数原理
```

**复合题型只占一个节点**，从两个入口查到的是同一个 ID。

考试压轴题几乎都是跨块的（圆锥曲线考向量、导数压轴考数列），
只能挂一处会直接漏题。

## 挂标签

录入时直接填：

```python
'topics': ['M-T-050']
```

已入库的题：

```bash
python3 py/main.py topic-link --payload '{"qid":"M-H0001","topics":["M-T-050"]}'
```

幂等，重复挂不会重复。

## 双向索引

```
题 目.topics    = ['M-T-135', 'M-T-156']
题 型.questions = ['M-H0001', 'M-2025-011']
```

**存储只存单向**（`题目的 topics` 是唯一权威），
反向索引每次加载时重建。双写必然不一致。

## 校验索引

```python
import sys; sys.path.insert(0, 'py')
import kp_catalog as K
bank = json.load(open('data/bank.json', encoding='utf-8'))
ok, problems = K.verify_index(bank)               # 默认不重建
ok, problems = K.verify_index(bank, rebuild=True)
```

| 破坏情形 | 检出方式 |
|---|---|
| 题型引用已删的题目（幽灵） | **默认模式（不重建）** |
| 题目挂了不存在的题型 ID | 两种模式都检出 |
| 反索引缺失 | 两种模式都检出 |

**默认不重建很关键**：rebuild 会用题目的 topics 整体覆盖 questions，
幽灵引用当场被洗掉，永远查不出来。

## 自动标注不可行（实测）

曾尝试自动把 422 个题型挂到 216 道题上：

| 匹配强度 | 命中 |
|---|---|
| 全特征词匹配 | **0 / 216** |
| 单特征词匹配 | **1 / 216** |

教辅题型名（「长方体模板1：三线垂直型」「错位相消法三种思维求法」）
和真题题干（「在三棱锥 A−BCD 中，平面 ABD⊥平面 BCD」）**语言几乎不重叠**。

**题型标签走人工标注。** 实测自动匹配命中率为 0（见上文数据），
所以流程上直接安排人工标，不在这上面花时间试算法。
反过来想，如果机器能判，说明这标签信息量也不大。


## 录入计划与进度跟踪

大批量录入前先生成任务清单，分批推进：

```bash
python3 tools/make_plan.py     # 产出 xlsx + md 两份清单
```

### 三个必须知道的数

| 项 | 处理 |
|---|---|
| 教辅总题数 1395 | 自动提取结果 |
| 重复题 15 | 题干+答案完全相同，保留首次出现的 |
| 已录题 | **必须手写映射表**，见下 |

### 已录映射要手写，不能靠自动匹配

`ref_bank` 的 key 用**题型内序号**（`M-T-009-V1`、`V2`），
而 PDF 页面上「变式演练」是**跨题型连续编号**（变式4、变式10…）。
专题7-2 下 变式1~3 属于题型一、变式4~6 属于题型二、变式7~9 属于题型三。

自动映射 41 题只匹配上 17 题 —— 已录题目被重复计入待录，
清单里会出现「T011 还没录」这种假象。

权威映射表在 `tools/_done_map.py`，按 答案 + 题型 逐一核对建立。
每录完一批要更新它。

### ref_bank 有漏提取

原 PDF 里答案写在详解末尾、没有【答案】标记的题，
自动提取时会被过滤（提取算法靠【答案】反向校验题号）。
第2批就补录了 2 道（M-T-009 典例、变式6）。

**实际录入量会比清单上的 1341 略多**，这是正常的。

### PDF 页码：按二级分组做窗口匹配

`tools/_toc_pages.json` 存 题型ID → PDF 页码，供快速翻原文用。

生成方法：对每个二级知识点，取其下所有题型（按 ID 序），
在 422 个 lv2 书签序列上**滑动窗口**找名字匹配度最高的位置。
同一个二级在 PDF 里是连续的，所以窗口内一定对齐。

不要试图用「题型名 + 所属专题名」直接匹配 ——
二级名与专题名经常不是包含关系
（如 二级「对称性与周期性」vs 专题「中心对称、轴对称与周期性归类」），
匹配率只有 67%。窗口法能做到 422/422。


### src 要写 ref_bank 的 key，不是 PDF 的连续编号

第3批起 src 格式改为：

```
'2024热点题型归纳 M-T-012-E1（典例）'
                  ^^^^^^^^^^^^ 完整 key
```

**为什么**：PDF 的「变式演练」跨题型连续编号，与 ref_bank 的题型内序号
（V1、V2）对不上。前两批用 PDF 编号，41 题只自动匹配上 17 题，
最后只能手写 `tools/_done_map.py` 兜底。

写入 key 后，`_done_map.done_keys()` 用一条正则就能提取，
100% 准确，后续批次无需再维护手写表。

**kind → key 后缀的换算**：`典例 → E1`，`变式N → VN`。
录入脚本里用 `suffix()` 函数统一转换，不要手拼。

### 已录判定统一走 done_keys()

```python
from _done_map import done_keys
keys = done_keys(bank)          # 新格式自动提取 + 旧格式查手写表
```

不要直接读 `DONE` 字典 —— 它只覆盖前两批，新批次不在里面，
会让已录题目被重复计入待录。

### check_render 的锚点要去半角下划线

`anchor_of()` 必须同时去掉全角 `＿＿＿＿＿` 和半角 `____`：

```python
s = re.sub(r'[＿_]{2,}', '', s)
```

只处理全角时，用半角录入的填空题会带着 `____` 做锚点，
而 `____` 在两端都被渲染成了 `blank-u` 元素（不在文本里）→
**整批填空题永久匹配失败**，表现为「核对 6/18 全军覆没」。

这个坑的隐蔽之处在于：选择题全过、填空题全挂，
很容易误判成「填空题渲染坏了」，实际渲染完全正常。

### 核对空位数要看题号，不要按 ID 顺序套块位置

渲染顺序由 `order_and_number` 按 `(科目, 题型序, 题号, id)` 重排，
**选择题在前、填空题在后**，与录入时的 ID 顺序不同。

用 `ids[i]` 直接对应 HTML 里的第 i 个块会得到错误的对应关系，
从而误判「某题空位异常」。

正确做法：从 HTML 块里提取题号 `<div class="qnum">N．</div>`，
按题号核对，而不是按 ID 位置推。


### 导出文件名禁用下划线

`--title "第3批_基本不等式"` 生成的文件名原本是 `试卷_第3批_基本不等式.html`。
把它写进 Markdown 回复后，两对下划线被解析成斜体标记：

```
试卷<em>第3批</em>基本不等式     ← 用户看到的
试卷_第3批_基本不等式.html       ← 实际文件名
```

下划线作为语法字符被吞掉，**用户看到的文件名少一截**，
且会误以为路径错误。连字符 `-` 不是 Markdown 语法，安全。

代码层已做归一（`sub_title.replace('_', '-')`），
所以即使 title 里写了下划线，落盘的文件名也是连字符：

```python
safe = (sub_title or '练习卷').replace('_', '-')
path = os.path.join(outdir, f'试卷-{safe}.html')
```

**命名规范**：批次产物用 `试卷-第N批-知识点.html`，
答案卷用 `答案与解析-第N批-知识点.docx`。

### 交付文件必须带闭合标签

回复里声明媒体文件时，`<media_info>` 必须有 `</media_info>` 收尾。
漏掉闭合标签时，整段 JSON 会以纯文本形式暴露给用户 ——
用户看到的是一行代码，而不是可下载的文件卡片。

自检：发出前确认结尾是 `</media_info>`。
